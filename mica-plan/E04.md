# E04 — When does Mica help, and when does it lose?

**Question:** Does Mica's speedup depend on how many rides match and whether those rides are close together or spread out in the input rows?

**Define cases from source rows, not pages.** Make two copies of the same NYC rides **before writing any format**. Sort whole rides by pickup time (with a fixed tie rule) for the grouped copy; randomly reorder whole rides with a saved seed for the scattered copy. Never shuffle columns separately. Within each copy, Mica, Parquet, and Lance get the **same row order**. The same query matches the same rides in both copies. Compare values, not output order unless requested.

Run **Mica, tuned Parquet, and indexed Lance** with settings fixed before timing. Return the same three columns in every case: pickup time, trip miles, and fare. Pick the two time ranges from source timestamps to get closest to the stated match fractions, then freeze them and check answers through E00.

| Case                     | Definition before writing Mica, Parquet, or Lance                                                                                                                                                            | What we learn                                                                 |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------- |
| **1: rare, grouped**     | Pick a pickup-time range matching about **0.01% of source rides**; write the time-sorted copy.                                                                                                               | Performance when few matches are adjacent in source row order.                |
| **2: rare, scattered**   | Use the **exact same time range and rides** as case 1; write the shuffled copy.                                                                                                                              | How changing only source row order changes the gap.                           |
| **3: medium, grouped**   | Pick a wider range matching about **1% of source rides**; write the time-sorted copy.                                                                                                                        | Effect of more matches when they remain adjacent.                             |
| **4: medium, scattered** | Use the **exact same time range and rides** as case 3; write the **same shuffled copy** as case 2.                                                                                                           | Effect of more matches when they are spread through the source rows.          |
| **5: frequent value**    | Keep the rides in the dataset's existing order, without sorting or shuffling. Find the dispatching-base ID (`dispatching_base_num`) that appears in the most rides. Ask for rides with that ID. Use the same ID and row order for every format. | How much each format can skip when the query matches many rides. |
| **6: no filter**         | Use the original source order and ask for the chosen columns from **every ride**, with no `WHERE` condition.                                                                                                 | Basic cost of reading the entire file, without filter work.                   |

**Reading the results:** Case 5 may still let a format skip data; a common value does not guarantee that every page contains a match. Case 6 is the no-filter control. The formats divide rows into different pages, so compare time and bytes read across formats. Raw page counts are not comparable across formats.

**What exists and what is needed:** Mica, Parquet, and Lance readers, Lance index preparation, and fixed NYC queries exist. Only the Parquet writer currently supports sorting. Add a shared sorted/shuffled input for all three formats, the two chosen time ranges, and a way to find the common dispatching-base ID. Check that read measurements work. These six cases have not been run.

**Record:** Check that all formats return the same rides. For repeated runs, record matches, query time, bytes read, and file size including indexes. Sorting can change file size, so use it when explaining timing differences. Show cases where Mica loses too.

**Next:** If row order changes the result, try one partly shuffled copy. If the rare and medium queries behave differently, try a match count between them. Investigate unexplained gaps through E02/E05 before attributing them to page layout.
