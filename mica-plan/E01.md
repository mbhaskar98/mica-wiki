# E01 — Does smaller-page pruning pay off?

**Question:** Do smaller pages save enough reading and decoding to compensate for the extra metadata and planning work?

**Metadata** means summaries, indexes, and page locations that help the reader decide what to read and where it is stored.

**Setup:** Same source rows/order, query answers, and declared resources, checked through E00. Use existing NYC point/range/compound and ClickBench equality/compound queries, plus a query reading much of the data.

**File variants:** Mica row-page caps **50 / 200 / 800 / 3200**. Parquet page-row targets **200 / 2000 / 20000** × row-group targets **1K / 16K / 256K / 1M**, where feasible. These are requested settings; record actual page sizes and splits.

**Native reference:** The full plan also calls for a sensible native baseline with a reuse-capable reader. It does not prescribe a Lance page-size sweep here; indexed Lance is explicitly compared in E02.
