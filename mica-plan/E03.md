# E03 — Does Mica still help when file maps are cached?

Each file stores a **map** of its columns, page locations, and information used to skip irrelevant pages. A reader reads the map's bytes and turns them into usable in-memory objects. The operating system may keep the **bytes**; the reader may keep the **objects**. Neither keeps final query answers in this test.

**Question:** When queries revisit files but memory cannot hold every file's map, does Mica still help compared with other readers allowed to reuse their maps?

Use file **A** to understand the first three tests:

| Test | What happens | What it measures | Existing → needed |
|---|---|---|---|
| **1. Nothing kept** | Remove the reader's map and verify A's map bytes are absent from the operating-system cache. Open A and run the query. Restarting the reader alone does not clear that cache. | Cost of reading and building the map for the first time. | Cold-read/cache-control tools exist → verify both caches are empty and reuse E01 runs only if their setup matches. |
| **2. Bytes kept** | Keep A's raw map bytes in operating-system RAM, but discard the reader and its usable map. Open A with a new reader and run the query. | Cost of rebuilding the map without fetching its bytes from disk. | Warm-page-cache measurements exist → create and verify this exact state for both readers. |
| **3. Map kept** | Keep the reader and its usable map after one query on A. Run another query on A with that reader; count the initial build once. | Benefit of reusing a prepared reader. This overlaps E01 point 3. | Mica prepared files and Parquet metadata-reuse modes exist → add a matched repeated-query runner and measure retained memory. |
| **4. Limited memory** | Keep one process running while queries visit A, B, C, and other files. Retain maps up to a memory limit; discard older ones when full. Revisiting an evicted file requires rebuilding its map. | **Main E03 test:** performance when reuse is possible but not every map fits. | Mica has an unbounded prepared-file cache; Parquet has single-file reuse controls → build byte-limited eviction, a multi-file query driver, and memory accounting. |

For test 4, try queries admitting **1, 8, and 64 files** where meaningful, and vary which files are revisited. Start with metadata limits of **0, 16, 64, 256, and 1024 MiB**, plus enough memory for all needed maps; adjust after measuring actual map sizes. Also test a verified **total-memory limit** that counts data cache and query buffers. Keep data-cache conditions comparable between readers.

**Record:** First-query time, total time for the query sequence, map rebuilds, metadata reads, evictions, and memory used.

**Status:** E03 has not been run.

**Comparators:** Start with Mica and Parquet. Indexed Lance already has benchmark code, but not E03 cache controls. Vortex and ORC are proposed E02 comparisons; this benchmark has no adapters for them yet. Add relevant native readers before making a broad claim across formats.
