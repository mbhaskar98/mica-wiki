# E02 — Which explanation accounts for the speed difference?

**Why E02 exists:** The paper tested Parquet's own page indexes/Bloom filters and cached metadata. It did **not** test Mica-style pruning metadata with Parquet data. E02 asks whether that metadata or Mica's data layout explains the gap.

| Lane | Action | Question |
|---|---|---|
| **P0** | Reuse E01's tuned native Parquet reader. | What can Parquet already do? |
| **P1, conditional** | If E01 exposes a specific reader bottleneck, patch it and rerun the same file/indexes; otherwise P1 = P0. | Was the gap avoidable reader work? |
| **P2** | Add Mica-equivalent pruning metadata beside unchanged Parquet files; build an adapter to use it. | Can the metadata approach work with Parquet data? |
| **P3, conditional** | If P2 loses due to mismatched column page boundaries, rewrite valid Parquet with verified aligned boundaries; retain P2's sidecar. | Is compatible layout enough? |
| **F** | Run full Mica. | What benefit remains? |

**P2 build:** Use the same ordered rows and actual Mica row intervals. Mica writes coarse/fine min/max for every column and chooses a Bloom (high cardinality) or exact bitmap (low cardinality; bitvecs belong to this bitmap) per column. Reuse index-building code where useful. For the matched test, give P2 equivalent information and verify **identical candidate intervals**; count all metadata bytes, build time and memory. Test reduced column coverage separately.

**P2 query:** Evaluate predicates against sidecar metadata, intersect their shared interval masks for `AND`, then convert survivors to Parquet row groups and `RowSelection`. Parquet reads its own pages and filters exact rows. A predicate on an unindexed column must be checked from Parquet data; an unindexed `OR` branch cannot be skipped. Each Parquet column has different physical page boundaries, so surviving rows may require pages containing rejected rows. **Existing:** Parquet `RowSelection` and reader. **Build:** sidecar writer, selective lookup, interval-to-Parquet-page mapping, adapter and file-identity checks.

**Other comparisons:** Build a conventional Parquet row-location index; run indexed Lance (reader/preparation exists) and relevant Vortex/ORC paths (adapters not found in this harness). [DataFusion external indexes](https://datafusion.apache.org/blog/2025/08/15/external-parquet-indexes/) and [parquet-index](https://github.com/lightcopy/parquet-index) show that external indexes with Parquet already exist. Inspect their actual granularity and compare runnable close alternatives before claiming a distinct design.

Start with **P0/P2/F** and closest existing controls. Measure query time, metadata/mapping work, reads, decoding, memory, and index build/storage cost. P2 candidates may include false positives; Parquet's exact filter remains required.
